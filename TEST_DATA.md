# Тестовые данные и сценарии

## Архитектура: две БД

```
   ┌────────────┐   read (SELECT)    ┌─────────┐   write (INSERT)   ┌────────────┐
   │  БД-1       │ ─────────────────▶ │ сервис  │ ─────────────────▶ │  БД-2       │
   │  source_db  │                    │ FastAPI │                    │  target_db  │
   │  :5442      │                    └─────────┘                    │  :5443      │
   └────────────┘                                                    └────────────┘
   division/position/employee                                        employee_transfer
```

Сервис читает сотрудников из **БД-1 (источник)** и переносит их в **БД-2 (приёмник)**.

**Главная цель тестирования** — эмулировать ошибки соединения с **БД-1** и убедиться,
что сервис делает **повторные запросы (retry)** и в итоге успешно завершает перенос
(либо корректно отдаёт ошибку, когда все попытки исчерпаны).

## Данные в БД-1 (источник)

Объёмы кратны 10 (генерируются `app/seed_source.sql`):

| Таблица   | Записей | Особенности                                             |
|-----------|---------|---------------------------------------------------------|
| division  | 10      | коды D01..D10, уникальные name/code                     |
| position  | 10      | грейд циклично 1..5                                     |
| employee  | 100     | распределены по 10 отделам, каждый 10-й `is_active=false` |

Данные детерминированы (по номеру строки), поэтому в тестах можно опираться на точные значения:
например, «активных сотрудников ровно 90», «в каждом отделе по 10 человек».

Легко масштабируется — поменять `generate_series(1, 100)` на `1, 1000` и т.д.

## Данные в БД-2 (приёмник)

Таблица `employee_transfer` (см. `app/schema_target.sql`) — стартует пустой.
После успешного переноса содержит перенесённые записи; `source_employee_id` уникален
(идемпотентность — повторный перенос не создаёт дублей).

## Сценарии retry (главное)

Как эмулируем обрыв соединения с БД-1 в тестах:

| Способ                        | Где применяется                                       |
|-------------------------------|-------------------------------------------------------|
| Мок соединения psycopg        | юнит/интеграционные тесты: connect кидает `OperationalError` первые N раз, затем успех |
| `docker compose pause db1`    | e2e-тест: реальный обрыв живой БД на время             |
| Неверный порт/хост в конфиге  | проверка, что после X попыток отдаётся понятная ошибка |

Проверяем:

1. **Успех после нескольких сбоев** — connect к БД-1 падает 2 раза, на 3-й успешен → перенос завершается, данные в БД-2 на месте, число попыток = 3.
2. **Исчерпание попыток** — connect падает всегда → сервис делает ровно `max_retries` попыток и возвращает ошибку (503/500), в БД-2 ничего не записано.
3. **Backoff** — между попытками выдерживается задержка (растущая); проверяем количество и интервалы вызовов.
4. **Идемпотентность/частичный перенос** — обрыв в середине не приводит к дублям в БД-2 (по `source_employee_id`).
5. **Ошибка только у БД-1** — сбои соединения не должны трогать/портить БД-2.

## Негативные кейсы данных (валидация)

| Кейс                          | Данные                    | Ожидаемо                    |
|-------------------------------|---------------------------|-----------------------------|
| Дубликат email в источнике    | `user1@example.com` ещё раз | IntegrityError (unique)   |
| Дубликат кода подразделения   | `D01`                     | IntegrityError (unique)     |
| Несуществующий division_id    | `9999`                    | FK violation                |
| Несуществующий position_id    | `9999`                    | FK violation                |
| Отрицательная зарплата        | `-100`                    | CHECK violation             |
| Повторный перенос сотрудника  | тот же `source_employee_id` | без дубля в БД-2 (unique) |

## Принципы

1. Каждый тест изолирован: пересоздаёт/очищает данные (schema + seed или транзакция с rollback).
2. БД-1 наполняется базовым seed; БД-2 стартует пустой.
3. Число попыток и задержки retry — конфигурируемы, чтобы тесты были быстрыми и детерминированными.
4. Данные фиксированы — тесты воспроизводимы.
