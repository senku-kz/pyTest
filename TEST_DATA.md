# Тестовые данные и сценарии

## Архитектура: две БД

```
   ┌────────────┐   read (SELECT)    ┌─────────┐   write (INSERT)   ┌────────────┐
   │  БД-1      │ ─────────────────▶ │ сервис  │ ─────────────────▶ │  БД-2      │
   │  source_db │                    │ FastAPI │                    │  target_db │
   │  :5442     │                    └─────────┘                    │  :5443     │
   └────────────┘                                                   └────────────┘
   division/position/employee                                        employee_transfer
```

Сервис читает таблицы из **БД-1 (источник)** — **поэтапно** (division → position →
employee) — и переносит сотрудников в **БД-2 (приёмник)**. Если первый этап чтения не
прошёл, остальные таблицы не читаются и запись не выполняется.

**Главная цель тестирования** — эмулировать ошибки соединения/чтения **БД-1** и убедиться,
что сервис делает **повторные запросы (retry)** и в итоге успешно завершает синхронизацию
(либо корректно отдаёт ошибку и пишет «Синхронизация НЕ выполнена», когда попытки исчерпаны).

## Данные в БД-1 (источник)

Объёмы кратны 10 (генерируются `sql/seed_source.sql`):

| Таблица   | Записей | Особенности                                               |
|-----------|---------|-----------------------------------------------------------|
| division  | 10      | коды D01..D10, уникальные name/code                       |
| position  | 10      | грейд циклично 1..5                                       |
| employee  | 100     | распределены по 10 отделам, каждый 10-й `is_active=false` |

Данные детерминированы (по номеру строки), поэтому в тестах можно опираться на точные значения:
например, «активных сотрудников ровно 90», «в каждом отделе по 10 человек».

Легко масштабируется — поменять `generate_series(1, 100)` на `1, 1000` и т.д.

## Данные в БД-2 (приёмник)

Таблица `employee_transfer` (см. `sql/schema_target.sql`) — стартует пустой.
После успешного переноса содержит перенесённые записи; `source_employee_id` уникален
(идемпотентность — повторный перенос не создаёт дублей). Очищается эндпоинтом
`DELETE /target`.

## Сценарии retry (главное)

Как эмулируем сбои БД-1 в тестах:

| Способ                       | Где применяется                                                              |
|------------------------------|------------------------------------------------------------------------------|
| Мок `psycopg.connect`        | юнит-тесты подключения: `connect` кидает `OperationalError` первые N раз.    |
| Мок курсора (`MagicMock`)    | юнит-тесты чтения: `execute`/`fetchall` возвращают данные или бросают ошибку |
| `docker compose pause db1`   | ручная/e2e-проверка: реальный обрыв живой БД                                 |

Тестам **реальная БД не нужна** — всё на моках (быстро и детерминированно).

Что проверяем (реализовано в `tests/test_source.py`):

**Подключение (`connect_source`):**
1. Успех с первой попытки — одна попытка, без пауз.
2. Успех после сбоев — падает, затем доступна → соединение получено.
3. Исчерпание попыток — падает всегда → ровно `RETRY_MAX_ATTEMPTS` попыток, затем ошибка.
4. Backoff — растущие паузы между попытками (`base`, `base*2`).
5. Параметры — подключение идёт с `connect_timeout`, `statement_timeout`, `tcp_user_timeout`, `autocommit`.

**Чтение (`read_table`):**
6. Успех сразу; повтор после обрыва соединения; повтор при отмене долгого запроса (`statement_timeout` → `QueryCanceled`); повтор при пустом ответе; исчерпание попыток; backoff.
7. Разнотипные ошибки соединения подряд → всё равно повтор и успех.
8. **Не-повторяемая ошибка** (например `ProgrammingError` — кривой SQL) НЕ ретраится, падает сразу.

**Поэтапность (`read_source`):**
9. Успех — все три таблицы читаются по порядку, возвращается `(divisions, positions, employees)`.
10. Одно соединение переиспользуется во всех чтениях.
11. **Short-circuit** — провал на любом этапе (1-м или 2-м) прерывает чтение, следующие таблицы не читаются.

**Оркестрация и запись** (`tests/test_transfer.py`, `tests/test_target.py`, `tests/test_api.py`):
12. При провале чтения пишется «Синхронизация НЕ выполнена», запись в БД-2 не идёт.
13. БД-2: подключение без повторов; идемпотентная запись; пустой список → без записи.
14. API: `/transfer` возвращает 503 при недоступности БД-1.

## Негативные кейсы данных (валидация)

Сценарии на уровне ограничений PostgreSQL (обеспечиваются схемой в `sql/`,
юнит-тестами приложения не покрыты):

| Кейс                          | Данные                    | Ожидаемо                    |
|-------------------------------|---------------------------|-----------------------------|
| Дубликат email в источнике    | `user1@example.com` ещё раз | IntegrityError (unique)   |
| Дубликат кода подразделения   | `D01`                     | IntegrityError (unique)     |
| Несуществующий division_id    | `9999`                    | FK violation                |
| Несуществующий position_id    | `9999`                    | FK violation                |
| Отрицательная зарплата        | `-100`                    | CHECK violation             |
| Повторный перенос сотрудника  | тот же `source_employee_id` | без дубля в БД-2 (unique) |

## Принципы

1. Юнит-тесты используют моки соединения (`MagicMock`) — реальная БД не нужна, каждый тест изолирован.
2. Число попыток и задержки retry — конфигурируемы (переменные окружения), а `sleep` в тестах подменяется → тесты быстрые и детерминированные.
3. Данные детерминированы (генерация по номеру строки) — воспроизводимость.
4. Для «живой» проверки БД-1 наполняется базовым seed; БД-2 стартует пустой.
