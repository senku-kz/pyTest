# pyTest — автотесты синхронизации двух БД

Учебный проект на **Python + FastAPI** для освоения автотестов. Сервис читает
данные из одной базы PostgreSQL и переносит их в другую.

**Главная цель обучения:** эмулировать **ошибки соединения с БД-1** и проверять
**повторные запросы (retry)** — как сервис переживает временный обрыв источника,
дожимает синхронизацию после нескольких попыток, а при исчерпании попыток
корректно сообщает об ошибке.

## Что делает сервис

```
   ┌────────────┐   читаем (SELECT)   ┌─────────┐   пишем (INSERT)   ┌────────────┐
   │  БД-1       │ ──────────────────▶ │ сервис  │ ─────────────────▶ │  БД-2       │
   │  source_db  │                     │ FastAPI │                    │  target_db  │
   │  :5442      │                     └─────────┘                    │  :5443      │
   └────────────┘                                                     └────────────┘
   division / position / employee                                     employee_transfer
```

- из **БД-1** читаются таблицы `division`, `position`, `employee` — **поэтапно**;
- если первый этап чтения не прошёл — остальные таблицы не читаются и запись не выполняется;
- в **БД-2** переносится «плоская» выгрузка сотрудников (идемпотентно, без дублей).

## Стек

- **Python + FastAPI** — веб-API
- **PostgreSQL ×2** — `source_db` (:5442) и `target_db` (:5443), обе через Docker
- **psycopg** (psycopg3) — драйвер PostgreSQL, работаем **чистым SQL** (без ORM)
- **pytest** + `unittest.mock` — автотесты (БД для тестов не требуется)

Стиль кода — **процедурный** (функции и константы, без классов), логи — через общий `logger`.

## Структура проекта

```
pyTest/
├── app/                    # Python-код
│   ├── main.py             # FastAPI: эндпоинты /health, /transfer
│   ├── config.py           # настройки — константы из окружения / .env
│   ├── logger.py           # общий logger
│   ├── db_source.py        # БД-1 (источник): подключение + поэтапное чтение с повторами
│   ├── db_target.py        # БД-2 (приёмник): подключение + запись
│   └── transfer.py         # оркестрация: читает из БД-1, преобразует, пишет в БД-2
├── sql/                    # SQL-скрипты
│   ├── schema_source.sql   # DDL БД-1: division, position, employee
│   ├── seed_source.sql     # наполнение БД-1 (10/10/100 записей)
│   └── schema_target.sql   # DDL БД-2: employee_transfer
├── tests/
│   ├── test_source.py      # БД-1: подключение + чтение (обрыв, таймаут, пусто, backoff)
│   ├── test_target.py      # БД-2: подключение без повторов + запись
│   ├── test_transfer.py    # оркестрация: маппинг + сообщение о провале
│   └── test_api.py         # эндпоинт /transfer
├── docker-compose.yml      # две PostgreSQL (db1 source, db2 target)
├── requirements.txt
└── .env.example            # пример настроек (скопировать в .env)
```

## Установка

Виртуальное окружение и зависимости:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

Настройки (необязательно — есть значения по умолчанию):

```bash
cp .env.example .env
```

## Запуск баз данных

Поднять обе БД:

```bash
docker compose up -d
```

Применить схемы и тестовые данные:

```bash
# БД-1 (источник): схема + 10/10/100 записей
docker exec -i pytest_db1_source psql -U app -d source_db < sql/schema_source.sql
docker exec -i pytest_db1_source psql -U app -d source_db < sql/seed_source.sql
# БД-2 (приёмник): схема
docker exec -i pytest_db2_target psql -U app -d target_db < sql/schema_target.sql
```

Остановить / удалить:

```bash
docker compose stop   # остановить (данные сохраняются)
docker compose down   # удалить контейнеры (данные пропадут — volume не используется)
```

## Запуск сервиса

```bash
uvicorn app.main:app --reload
```

- API: http://127.0.0.1:8000
- Swagger UI: http://127.0.0.1:8000/docs

Эндпоинты:

| Метод | Путь | Описание |
|------|------|----------|
| GET    | `/health`   | проверка живости |
| POST   | `/transfer` | запустить синхронизацию БД-1 → БД-2 |
| DELETE | `/target`   | очистить таблицу-приёмник в БД-2 |

Примеры:

```bash
curl -X POST   http://127.0.0.1:8000/transfer   # синхронизация → {"read": 100, "inserted": 100}
curl -X DELETE http://127.0.0.1:8000/target     # очистка приёмника → {"deleted": 100}
```

Если БД-1 недоступна и повторы исчерпаны → HTTP 503, `Синхронизация не выполнена: БД-1 недоступна`.

## Запуск автотестов

БД для тестов **не нужна** — соединения мокаются (`MagicMock`), тесты быстрые и детерминированные.

```bash
pytest tests/test_source.py -v
pytest              # все тесты
pytest -v           # подробный вывод
pytest tests/test_source.py   # только тесты БД-1
pytest -k retries   # по маске имени
```

Что покрыто:

- **БД-1 (чтение):** повтор подключения, обрыв соединения при чтении, отмена долгого
  `SELECT` (`statement_timeout` → `QueryCanceled`), пустой ответ, backoff, исчерпание попыток;
- **поэтапность:** если первый этап чтения упал — остальные таблицы не читаются;
- **провал синхронизации:** пишется сообщение «Синхронизация НЕ выполнена», запись в БД-2 не идёт;
- **БД-2 (запись):** подключение без повторов, идемпотентная вставка.

## Эмуляция обрыва БД-1 вручную

Для «живой» проверки retry можно поставить источник на паузу и дёрнуть `/transfer`:

```bash
docker compose pause db1     # обрыв
curl -X POST http://127.0.0.1:8000/transfer           # → 503 после N попыток
docker compose unpause db1   # восстановление
```

## Настройки (переменные окружения)

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `SOURCE_DSN` | `postgresql://app:app@localhost:5442/source_db` | подключение к БД-1 |
| `TARGET_DSN` | `postgresql://app:app@localhost:5443/target_db` | подключение к БД-2 |
| `RETRY_MAX_ATTEMPTS` | `3` | сколько попыток на подключение/чтение БД-1 |
| `RETRY_BASE_DELAY` | `0.2` | базовая пауза между попытками (растёт ×2) |
| `CONNECT_TIMEOUT` | `2` | таймаут установки соединения, сек |
| `STATEMENT_TIMEOUT_MS` | `3000` | серверный таймаут на запрос (долгий SELECT → ошибка → повтор) |
| `TCP_USER_TIMEOUT_MS` | `3000` | таймаут «молчащего» сокета (зависший сервер → ошибка → повтор) |
